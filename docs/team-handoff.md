# Team handoff

The immediate October 8 goal is a repeatable demonstration of two live MCP
servers. The architecture keeps responsibilities separate while allowing the
initial integration to be implemented together.

| Owner | Files / interface | Next responsibilities |
|---|---|---|
| Person 1 | `cli.py`, `agent.py`, `dispatcher.py`, `policy.py`, `commands.py` | Stabilize autonomous task completion, terminal experience, approvals, command reporting |
| Person 2 | `mcp_client.py`, server configuration; `MCPHub` | Connection lifecycle, discovery, filesystem behavior, server configuration |
| Person 3 | Future custom RAG MCP server | Persistent vector storage, chosen corpus, indexing, advanced RAG, retrieval tools |
| Person 4 | `providers/`, external server config, provider setup | Context7/Fetch, AWS Bedrock and Ollama implementations, evaluation |

Shared contracts are in `src/edric/contracts.py` and documented in
`docs/implementation-contracts.md`. Tool calls retain their IDs; every result,
including denied or failed actions, returns to the next model turn. Public tool
names are mapped to discovered original names and server identity.

## Extending the system

A new MCP server should be configured and dynamically discovered by `MCPHub`.
Person 3's RAG tool can then be supplied to the agent through the same registry.
Agree on retrieval arguments and output fields before implementing the corpus.
Treat retrieved text as source material; report provenance and retrieval failures.

A new provider implements `Provider.complete(messages, tools, on_text)` and
returns `ModelTurn`, including the provider continuation data needed after tool
calls. AWS and Ollama adapters must be implemented and tested before being
described as working. Model availability and AWS costs must be checked before
enabling live paid requests; the project has no automatic paid-provider fallback.

The HTTPX demo fixture is generated by `prepare_demo_workspace`. It includes
offline behavioral tests. `run_checkin_demo` is explicitly predetermined and
uses actual MCP calls. An autonomous Groq run is a separate verification step.

## Merge and verification guidance

Coordinate files before editing; do not overwrite another member's work. Keep
credentials in ignored local configuration or environment variables. Record
dependency changes and setup commands. Run the focused tests and relevant live
integration after changing the tool/provider contracts. A mock test validates
application behavior but does not establish that a server or provider works.

Before October 15, agree on the RAG corpus and advanced technique, implement
Ollama and the selected cloud provider, evaluate task outcomes across models,
and prepare the required architecture diagrams, report, and video. See the
assignment PDF for the exact final rubric.
